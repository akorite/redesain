\chapter{The memory hierarchy}
\label{ch:systems09}
\index{memory hierarchy}\index{cache}\index{locality}

Chapters 5--8 built a machine that retires one instruction per cycle.
That claim hides an assumption this chapter finally confronts:
\emph{every memory access takes one cycle}. It does not. A load
that hits L1 costs $\approx$1.4\,ns here; the same load missing to
DRAM costs 120\,ns --- an 85$\times$ swing the pipeline papers over
with stalls you cannot see in a functional simulator. This chapter
measures the real hierarchy on the machine in front of you, names
the two localities that make it work, and turns the numbers into the
contract every later chapter leans on.

\begin{rulebox}[After this chapter you can]
You will be able to write a small C program that measures how long one
memory read takes for a given amount of data, run it, and read the
result as a staircase: fast for small data, slower in steps as the data
grows. You will be able to say what each step is (a cache level, or
main memory), explain why a sequential walk and a random walk behave
differently, and avoid the three classic mistakes that make such a
measurement lie.
\end{rulebox}

\begin{rulebox}[Before you start]
\emph{What a memory read costs.} In Book~1 chapter~1 (the contest
machine and the cost model) we pretended that reading a variable costs
one step. Chapters~5--8 of this book kept that pretence: a load takes one
clock cycle. A \emph{clock cycle} is one tick of the processor's
metronome; at 3\,GHz there are three billion ticks per second, so one
tick is about a third of a nanosecond (1\,ns is a billionth of a
second). This chapter is where the pretence ends.

\emph{A five-line C refresher.} The programs here are in C, so here is
all the C you need to read them.
\texttt{uint64\_t x;} is a 64-bit whole number (8 bytes).
\texttt{uint64\_t *a;} says ``\texttt{a} is the address of such a
number''; \texttt{a[i]} is the \(i\)-th number at that address,
and \texttt{malloc(n)} asks the system for \(n\) bytes of memory.
A pointer is just an address stored in a variable, and
\texttt{*p} means ``read the number stored at address \texttt{p}''.
\texttt{for (long r = 0; r < reps; r++) \{ ... \}} repeats its body
\texttt{reps} times. The keyword \texttt{volatile} tells the compiler
``do not optimise this variable away; really read and write it each
time''. Finally, \texttt{clock\_gettime} returns a stopwatch reading;
we subtract two readings to time a loop.
\end{rulebox}

\begin{rulebox}[Think like this]
A measurement is an experiment, and an experiment needs a hypothesis.
Before running any benchmark in this chapter, write down in one line
what you expect to see and why. When the number disagrees, the
disagreement is the interesting part: either your picture of the
machine is wrong, or your program is not measuring what you think.
\end{rulebox}

\section{Why there is a hierarchy at all}
\label{sec:why09}

Here is an everyday picture. You are studying at a desk. The book you
are reading lies open in front of you (instant). Other books sit on a
shelf behind you (a few seconds). The rest are in the library across
town (an afternoon). Nobody would call this a design flaw: a desk big
enough for the whole library would not fit in your room. A computer
makes exactly this trade, for exactly this reason.

The ideal memory is fast, huge, and cheap. Physics offers any two.
The SRAM bit-cell that feeds a 3\,GHz pipeline uses six transistors
--- fast, and so large that a gigabyte of it would be a dinner plate.
The DRAM cell that makes gigabytes affordable is one transistor and
a leaky capacitor --- dense, and so slow it answers in tens of
nanoseconds and needs refreshing every $\sim$64\,ms. Nobody
compromised; the hierarchy is the compromise.

\input{figures/ch09/fig_sramdram.tex}

\begin{example}[The compromise in one number]
On this machine the register file answers in $\approx$0.3\,ns and
DRAM in $\approx$120\,ns --- 400$\times$. If every load went to DRAM,
our ``one instruction per cycle'' core would retire one instruction
per \emph{hundred} cycles. The hierarchy exists so that
\emph{most} loads never take the slow path.
\end{example}

\section{The memory mountain, measured}
\label{sec:mountain09}

The classic experiment: build a circular linked list whose elements
are scattered randomly through a working set, then chase it. Every
load's address depends on the previous load's value, so the CPU's
prefetcher and out-of-order engine cannot run ahead --- each access
pays the true latency of whichever level happens to hold the set.
\texttt{ch09\_mem\_mountain.c} does exactly this, for sets from
4\,KB to 128\,MB, 20 million dereferences each.

\begin{lstlisting}[language=C,caption={The heart of
\texttt{mem\_mountain.c}: the dependent-load chain.}]
for (size_t i = 0; i < n; i++)
    a[perm[i]] = (uintptr_t)&a[perm[(i + 1) % n]];
volatile uintptr_t p = (uintptr_t)&a[perm[0]];
for (long r = 0; r < reps; r++)
    p = *(volatile uintptr_t *)p;   /* load depends on last load */
\end{lstlisting}

\begin{example}[What the author's Mac answered]
Verbatim output from the author's Apple-silicon Mac (arm64, macOS;
the full log is in \texttt{code/ch09\_mountain.dat}). The Linux x86\_64
container numbers come later in this section and differ, which is the
point:

\begin{verbatim}
   bytes    ns/load
   16384       1.40
  131072       1.45
  262144       4.70
 8388608      10.21
16777216      26.36
134217728     120.64
\end{verbatim}

Four regimes on one arm64 part: $\approx$1.4\,ns through 128\,KB
(L1/L2), a knee to 4.7\,ns at 256\,KB, a 5--10\,ns plateau to
16\,MB (the system-level cache), then the climb to 120\,ns of DRAM.
Those dashed knees in figure~\ref{fig:mountain09} \emph{are} your
cache sizes, read off silicon rather than a data sheet.
\end{example}

\input{figures/ch09/fig_mountain.tex}

\begin{checkpoint}
Why a \emph{random} chain and not sequential pointer-chasing? A
sequential walk has stride 8\,bytes; the prefetcher learns it in
three accesses and the ``latency'' you measure is just bandwidth.
The random permutation forces every level to reveal itself.
\end{checkpoint}

\begin{example}[Reading a second machine's staircase]
Read the Linux table as steps. Up to 32\,KiB the time is flat at about
3\,ns: the data fits in L1. At 64--512\,KiB it is 4.5--7.4\,ns: L1 has
overflowed, and the loads now come from L2. At 1--2\,MiB it is
14--19\,ns, and past 4\,MiB it jumps to about 100\,ns and then 130--200\,ns.
The step positions (32\,KiB, then about 1\,MiB) match what \texttt{getconf}
reports for L1 and L2, which is a check that the experiment measures
what we think. Two surprises are worth saying aloud. First, the
100\,ns at 4\,MiB is far below the 33\,MiB L3 size the container
advertises; we did not isolate why (a virtual machine shares that
cache with other tenants, and its page mapping is not ours to control),
so we do not claim an L3 plateau. Second, even the L1 rows say 3\,ns,
roughly 8 clock cycles at 2.8\,GHz, while an L1 hit should be about 4--5
cycles. The next example explains the surplus.
\end{example}

\begin{example}[The benchmark taxes itself: what \texttt{volatile} costs]
Our chain loop declares the pointer \texttt{volatile}, so that the
compiler cannot delete the loop. A naive reading says ``that only
protects the measurement''. Test it. \texttt{ch09\_volatile\_cost.c}
times the same 4\,KiB chain, always an L1 hit, twice:

\begin{lstlisting}[language={},caption={Linux x86\_64 container,
\texttt{./ch09\_volatile\_cost}: the same L1-resident chain with a plain
and a \texttt{volatile} pointer.}]
plain pointer   : 1.26 ns/load  (0)
volatile pointer: 2.93 ns/load
\end{lstlisting}

The plain loop runs at 1.26\,ns, about 3.5 cycles per load at the nominal 2.8\,GHz, which is a
believable L1 latency. The \texttt{volatile} loop is 2.3 times slower,
because every step now also stores the pointer to memory and reads it
back before the next load can start. So the staircase above is a true
staircase sitting on a floor of roughly 1.7\,ns of bookkeeping. The
\emph{shape} survives, and the knees are still right; the absolute
numbers in the low rows are inflated. When you meet a benchmark number,
ask what the loop itself costs.
\end{example}

\begin{example}[Latency versus throughput: the independent-loads mistake]
The checkpoint above warned that independent loads measure the wrong
thing. Here is the proof. \texttt{ch09\_dep\_vs\_indep.c} visits the
\emph{same} random order two ways. In the dependent version each address
is the value just loaded (\texttt{p = a[p]}), so the processor must wait
for each answer. In the independent version the addresses come from a
separate array of indices (\texttt{s += a[idx[k]]}), so the processor can
send many requests at once and overlap the waiting.

\begin{lstlisting}[language={},caption={Linux x86\_64 container,
\texttt{./ch09\_dep\_vs\_indep}: 20 million loads per row, same random
visiting order, dependent versus independent (4-byte elements).}]
     bytes  dep ns/load indep ns/load    ratio
     32768         1.71         1.12     1.5x   (check 7035 1)
   1048576        10.53         2.04     5.2x   (check 231304 0)
   8388608       135.61        12.03    11.3x   (check 157217 1)
 134217728       194.30        23.93     8.1x   (check 30533386 1)
\end{lstlisting}

In L1 the two are close (1.7 versus 1.1\,ns): there is nothing to hide.
At 8\,MiB and beyond the dependent chain pays the full 135--194\,ns per
load while the independent version averages 12--24\,ns, as if roughly
8 to 11 requests were overlapped in flight at once (an inference from
the ratio, not a hardware counter reading). Same data, same order, same
machine, an 8 to 11 times difference in the answer. If the question is
``how long does one cache miss take?'', only the dependent chain answers
it; the independent loop answers ``how many misses per second can the
memory system sustain?''. Both are real numbers about the machine.
They are different numbers.
\end{example}

\section{Locality: the only two tricks caches know}
\label{sec:locality09}

A 4\,KB L1 cannot hold a 4\,GB program. It doesn't have to, because
real programs are lumpy in exactly two ways:

\begin{itemize}
\item \textbf{Temporal locality}: an address used once is likely to
      be used soon again (loop counters, stack, hot data).
\item \textbf{Spatial locality}: an address near a used one is likely
      to be used soon (arrays, sequential code, adjacent fields).
\end{itemize}

Caches exploit both: they keep recently-used lines (temporal) and
fetch them 64 or 128 bytes at a time (spatial). Neither is a law ---
they are statistical bets, and figure~\ref{fig:stride09} shows what
it costs to lose the spatial one.

\input{figures/ch09/fig_locality.tex}

\begin{example}[Effective access time, honestly]
Suppose L1 hits at 95\% and misses cost 10\,ns. Then
$\text{EAT} = 0.95 \times 1.4 + 0.05 \times 10 \approx 1.8$\,ns.
Drop hit rate to 85\% and EAT rises by almost half, to 2.7\,ns --- the
hierarchy's economics live in the last few percent of hit rate,
which is why the next two chapters exist.
\end{example}

\section{Bandwidth has a stride too}
\label{sec:stride09}

Latency is half the story. \texttt{ch09\_stride\_bw.c} reads a
64\,MiB array at increasing strides --- same total read, different
bytes pulled across the bus per useful access.

\begin{example}[The stride cliff, measured]
\begin{verbatim}
stride     ns/acc    GB/s(eff)
     1      1.073         7.45
     8      1.032         7.75
    16      3.693         2.17
    32      3.780         2.12
\end{verbatim}

Elements are 8 bytes, so a stride of 8 means each access lands on its
own 64-byte cache line. The bus then moves 64 bytes to deliver 8 useful
ones, for stride 8 as for every larger stride. On the Mac the time per
access is flat up to stride 8 and then triples at stride 16, where the
accesses stop landing on consecutive lines. We measured this cliff but
did not isolate its mechanism (the stride-128 dip in the data is
likewise unexplained), so treat ``the hardware prefetcher gives up''
as a plausible story, not a finding. This is the column-order traversal
trap every matrix chapter returns to.
\end{example}

\begin{example}[The same experiment on Linux x86\_64]
\begin{lstlisting}[language={},label={lst:stridelinux09},caption={Linux x86\_64 container,
\texttt{./ch09\_stride\_bw}: 64\,MiB array, 8-byte elements, 20 sweeps
per stride. Captured in \texttt{code/ch09\_stride\_linux.txt}.}]
stride     ns/acc    GB/s(eff)
     1      2.103         3.80
     2      2.660         3.01
     4      4.239         1.89
     8      7.477         1.07
    16     14.154         0.57
    32     15.639         0.51
    64     14.166         0.56
   128     14.696         0.54
\end{lstlisting}
There is no sharp cliff here; the cost per access climbs smoothly from
2.1\,ns at stride 1 to about 14\,ns at stride 16 and then stays flat.
Both machines agree on the lesson: the time per access stops growing
once every access owns a cache line, which on this container happens
by stride 16 (stride 8 already costs 3.6 times stride 1). (Stride 1
and 2 are partly limited by the \texttt{volatile} accumulator, as in the
previous example.) Where the knee falls is a property of the machine;
that it exists is a property of cache lines.
\end{example}

\section{Common mistakes}
\label{sec:mistakes09}
\index{memory mountain}

\begin{itemize}
\item \textbf{Measuring latency with independent loads.} An
      out-of-order core overlaps a hundred of them; you measure
      throughput, not latency. The chain must be \emph{dependent}.
\item \textbf{Believing ns numbers without the working set.} 1\,ns
      at 8\,KB and 1\,ns at 8\,MB are different phenomena ---
      latency is a function of footprint, not a constant.
\item \textbf{Assuming a cache line is a word.} The stride
      experiment's whole point: the unit of transfer is 64--128
      bytes. ``I only read 8 bytes'' still moves the whole line.
\item \textbf{Optimising for a level that isn't the bottleneck.}
      Fixing L1 behaviour while the working set lives in DRAM is a
      rounding-error improvement --- find your knee first.
\item \textbf{Treating prefetchers as magic.} They learn
      \emph{regular} patterns; a random-access structure (hash
      table, pointer graph) defeats them completely.
\end{itemize}

\section*{Exercises}
\addcontentsline{toc}{section}{Exercises}
\stepcounter{section}

\begin{exercise}[easy]

From our mountain data, estimate the latency ratio between a
register read and a DRAM read on this machine. Then express DRAM
latency in ``human scale'': if L1 were one second away, how far is
DRAM?
\end{exercise}
\begin{solution}[hint]
0.3\,ns vs 120\,ns; scale 1.4\,ns$\to$1\,s.
\end{solution}

\begin{exercise}[easy]

A program scans a 100\,MB array twice. Between scans, nothing else
runs. Which locality saves the second scan, and which cache level
does it live in?
\end{exercise}
\begin{solution}[hint]
100\,MB exceeds every level; the second scan is as cold as the
first --- no level helps.
\end{solution}

\begin{exercise}[easy]

Why does the pointer-chase use a \emph{circular} list and not a
linear one?
\end{exercise}
\begin{solution}[hint]
Same traversal cost for warmup and measurement; no
unpredicted tail.
\end{solution}

\begin{exercise}[easy]

Name the two localities and give one C construct that exhibits each.
\end{exercise}
\begin{solution}[hint]
Loop variable vs.\ array walk.
\end{solution}

\begin{exercise}[medium]

Predict, then verify with \texttt{stride\_bw}: does a stride-64 read
of a 64\,MiB array transfer the same total bytes over the bus as
stride-1? What \emph{does} change?
\end{exercise}
\begin{solution}[hint]
Same array is swept; useful bytes per fetched line changes
8$\times$.
\end{solution}

\begin{exercise}[medium]

Our EAT example assumed one miss cost. Real misses chain: an L1 miss
may hit in L2. Extend the formula to three levels and compute EAT
for L1=95\% (1.4\,ns), L2=90\% (5\,ns), DRAM base 120\,ns.
\end{exercise}
\begin{solution}[hint]
Model: every access pays the L1 lookup (1.4\,ns); on the 5\% that miss, pay 5\,ns for L2, and on the 10\% of those that also miss, 120\,ns more.
EAT $=1.4+0.05\,(5+0.10\times120)=1.4+0.05\times17=2.25$\,ns.
\end{solution}

\begin{exercise}[medium]

The mountain's L1/L2 knee sits between 128\,KB and 256\,KB on this
part. Bisect the size sweep to pin the L2 boundary to one binary
digit; describe how you'd distinguish L1-vs-L2 knees from a
SLC-vs-DRAM knee.
\end{exercise}
\begin{solution}[hint]
Re-run with sizes $2^{17.5}$, $2^{18.5}$; the DRAM knee's
slope is far steeper.
\end{solution}

\begin{exercise}[medium]

A colleague optimises a hash table for ``cache friendliness'' by
shrinking each entry. Why might that \emph{not} help, given what
the stride experiment showed about the unit of transfer?
\end{exercise}
\begin{solution}[hint]
Random access means each probe fetches a whole line; entry
size matters only at line granularity.
\end{solution}

\begin{exercise}[hard]

Infer L1 line size and associativity \emph{from stride experiments
alone}: given only \texttt{stride\_bw}-style timing over varying
strides and sets, describe the experimental protocol that pins down
the line length, then the associativity. What measurements disambiguate
a 64B/4-way cache from a 128B/2-way one?
\end{exercise}
\begin{solution}[hint]
Stride-vs-capacity curve gives line size; associativity needs
conflict misses --- sweep $k$ addresses spaced at set-straddle
distance.
\end{solution}

\begin{exercise}[hard]

Our mountain flattens at 120\,ns for DRAM. Row-buffer hits make real
DRAM cheaper than the worst case. Design the experiment that
separates row-hit from row-miss latency, and predict the two numbers
for a system whose mountain you haven't run yet.
\end{exercise}
\begin{solution}[hint]
Same-bank adjacent-column accesses vs.\ alternating-bank
accesses; expect 40--60\,ns vs.\ 80--120\,ns class numbers.
\end{solution}

\begin{exercise}[hard]

Argue that temporal locality is a program property, not a hardware
property --- then explain why the \emph{effectiveness} of exploiting
it is a hardware property. Use the blocked-transpose preview from
ch10's forward reference.
\end{exercise}
\begin{solution}[hint]
Reuse distance is fixed by the code; whether it fits is set by
capacity and associativity.
\end{solution}

\begin{exercise}[easy]
From the contract table, which level is managed by software you
write (not the compiler, not hardware, not the OS page allocator)?
\end{exercise}
\begin{solution}[hint]
None --- registers are the closest you get, and the ISA owns
those. That is the point: caching is a hardware service.
\end{solution}

\begin{exercise}[medium]
\texttt{mem\_mountain} reports ns/load, not cycles. Convert our
1.4\,ns and 120\,ns numbers to cycles on a 3.5\,GHz core, and
state in one line why cycle-counting is the unit that matters to a
pipeline.
\end{exercise}
\begin{solution}[hint]
4.9 and 420 cycles; the stall counter is what the core sees.
\end{solution}

\begin{exercise}[medium]
The stride cliff lands between 8 and 16 elements. What does that
imply about this machine's cache line size in bytes, and how would
you test the hypothesis with one more run?
\end{exercise}
\begin{solution}[hint]
64B lines: stride 8 fits 8 accesses/line; stride 16 overflows.
Sweep elements, not bytes.
\end{solution}

\begin{exercise}[hard]
Some systems advertise an ``effective'' memory latency far below
DRAM's 120\,ns. Reconcile that marketing number with your mountain:
under what access pattern is it true, and what pattern exposes the
real number? Name the benchmark trick being used.
\end{exercise}
\begin{solution}[hint]
Sequential/streaming lets prefetch hide latency ---
SPEC-style streams vs. dependent pointer chase.
\end{solution}
