\chapter{A Single-Cycle RV32I Core}
\label{ch:sc05}
\emergencystretch=3em

Assembly language is the contract; this chapter builds the machine
that honours it. Everything so far --- the encodings of ch03, the
frames of ch04, the cpu8 of Book 5 --- meets in one Verilog module:
a single-cycle RV32I core that fetches, decodes, executes, touches
memory, and writes back in one clock tick. Book 5 built the blocks
(an 8-bit ALU, a register file, a control decoder); here they are
re-derived at 32 bits against the real ISA --- compute-all-then-mux
ALU, two-read one-write regfile with \texttt{x0} hardwired, and a
decoder that is literally a truth table in Verilog. The core runs real
programs in Icarus, and every run is checked against an independent
reference. CPI is 1 by construction --- the point of the chapter is
seeing \emph{why that is a waste of time}, which is the whole argument
for the pipeline of ch06.

\begin{wins}[What you will be able to do after this chapter]
You will be able to take a short RV32I assembly program, assemble it
to machine words, run it on a processor you can read line by line,
and \emph{prove} the result is right by comparing the processor's
final registers and memory against a second, independent model. You
will be able to take any 32-bit instruction word and split it into
its fields by hand, including the tricky scattered immediates. And
you will be able to explain, with numbers, why this simple design is
correct but slow.
\end{wins}

\begin{rulebox}[Before you start]
This chapter leans on four things you have met before; here is each
one in a few lines, so you do not need to go back.
\emph{Bits and gates} (Book 5, ch08--09): a signal is a wire that is
either 0 or 1; a group of 32 wires carries a 32-bit number; a
\emph{multiplexer} (``mux'') is a switch that passes one of several
inputs, chosen by a select wire; an adder is a pile of gates that
turns two numbers into their sum with no clock at all. Circuits made
only of such gates are called \emph{combinational}: the output is a
pure function of the inputs right now.
\emph{Clocks and registers} (Book 5, ch10): a \emph{register} (built
from flip-flops) is a box of bits that copies its input only at the
instant the clock ticks, and otherwise holds still. Circuits with
registers are \emph{sequential}: they have memory. One tick of the
clock is one \emph{cycle}.
\emph{Verilog} (Book 5, ch11--12): a text language that describes
wires, registers and gates; a \emph{module} is one box with named
ports; a \emph{testbench} is a second module that drives the clock,
feeds inputs, and prints or checks what comes out.
\emph{The ISA} (Book 7, ch03--04; Book 5, ch14--16): RV32I has 32
registers \texttt{x0}--\texttt{x31} of 32 bits, and every instruction
is one 32-bit word whose bit fields name the operation, the registers
and a constant (the \emph{immediate}). Book 5 ended with a small
8-bit CPU (the ``cpu8'': ALU, register file, control); this chapter is
the same machine, rebuilt at 32 bits for the real instruction set.
\end{rulebox}

\section{The idea from zero: a machine that follows a recipe}
\label{sec:zero05}
\index{program counter}\index{state}

Picture a cook following a recipe book. The cook keeps one finger on
the current line. At each step the cook reads the line, does exactly
what it says with the bowls on the bench (``add the contents of bowl
10 and bowl 11, put the result in bowl 12''), and then moves the
finger to the next line, unless the line said ``jump back to line
7''. That is the whole of a processor. The finger is the \emph{program
counter} (\texttt{pc}): a 32-bit register holding the address of the
current instruction. The bowls are the \emph{register file}. The
pantry down the corridor, bigger but slower to reach, is
\emph{memory}. The metronome the cook obeys is the \emph{clock}.

\begin{principle}[Think like this: state and a function]
Every digital machine can be described by two things. The
\emph{state} is everything that is remembered between ticks: here the
\texttt{pc}, the 32 registers and the memory. The \emph{function} is
the combinational logic that, given the state, works out the
\emph{next} state. On each tick the machine does
$\text{state}\leftarrow f(\text{state})$ and nothing else. When a
processor misbehaves, ask two questions in order: ``what was the state
before the tick?'' and ``what should $f$ have produced?'' Almost every
bug in this book is an answer to one of those.
\end{principle}

Why build it this way? Because it makes one instruction cost exactly
one tick, which is the simplest thing to reason about: no instruction
ever overlaps another, so the machine is correct whenever each
instruction is. Its price, as the last section measures, is a slow
clock.

\section{Fetch--decode--execute, properly}
\label{sec:fde05}
\index{single-cycle processor}\index{datapath}\index{RV32I core}

Ch03 drew the loop as fetch $\to$ decode $\to$ execute $\to$ next.
The honest version splits execute into three: read operands, compute
in the ALU, touch data memory, write the result back --- five acts,
all inside one clock period. The program counter is the only state
element outside the register file and memories: an \texttt{insn} wire
from instruction memory, a \texttt{pc} register, and a next-pc mux.
Everything else is combinational logic evaluating the current
instruction \emph{right now}. That is the definition of
single-cycle: latency of one instruction $=$ one clock period.

\section{Decode and the immediate generator}
\label{sec:decode05}
\index{immediate generator}\index{decoder}

\begin{example}[decode is a table]\label{ex:ctrl05}
\texttt{ch05\_rv32i\_decode.v} has no cleverness: a \texttt{case}
on the 7-bit opcode, defaults that make an unknown word a NOP. For
\texttt{sw} ($\texttt{op}=0100011$): \texttt{alusrc=1, memwrite=1,
aluop=add} --- base register plus immediate for the address,
\texttt{rd2} already carries the value to store. The truth-table

\end{example}

\begin{example}[the immediate mux]\label{ex:immgen05}
The five formats of ch03 produce five bit-shuffles: \texttt{immI}
sign-extends \texttt{insn[31:20]}; \texttt{immS} splices
\texttt{[31:25]} and \texttt{[11:7]}; \texttt{immB} and
\texttt{immJ} reorder the same window into jump offsets;
\texttt{immU} just shifts. One mux selects among them on opcode ---
the scrambler is about fifteen lines of wiring.
\end{example}

\section{Register file and ALU --- Book 5, widened}
\label{sec:reused05}
\index{register file}\index{ALU}

\begin{example}[the cpu8 mapping, honoured]\label{ex:mapping05}
Book 5's ch14 ALU chose its result by mux after computing all ops;
\texttt{ch05\_rv32i\_alu.v} is the same shape at 32 bits, nine ops
(add, sub, and, or, xor, sll, srl, slt, sltu). The regfile keeps
Book 5's
two-read/one-write shape and adds the RV32I rule that made
\texttt{x0} famous: \texttt{(ra1==0)\ ?\ 0\ :\ x[ra1]} \emph{and}
\texttt{we \&\& wa!=0} --- write \texttt{x0} and the write is
silently dropped, which is exactly how the ISA wants it.
\end{example}

\begin{principle}[Concept: why the register file must read without a clock]
An instruction like \texttt{add a2,a0,a1} needs two register values
\emph{at the same moment} to feed the ALU, in the same cycle that it
fetches. If reading required a tick, every instruction would take two.
So the read ports are plain combinational multiplexers: put an index on
\texttt{ra1}, and \texttt{rd1} follows after a gate delay. Only the
write waits for the clock edge. Reads are free-running, writes are
scheduled.
\end{principle}

\section{Loads, stores and the data-memory interface}
\label{sec:mem05}
\index{load/store}\index{data memory}

Both \texttt{lw} and \texttt{sw} run the ALU as an address adder:
\texttt{rd1} (base) plus the immediate. The difference is which end
of data memory lights up --- \texttt{memread} routes
\texttt{dmem\_rdata} through the writeback mux into \texttt{rd};
\texttt{memwrite} drives \texttt{dmem\_we} with \texttt{rd2} on the
data pins. Addressing mode coverage is deliberately tiny: RV32I has
exactly one addressing mode (base+imm), which is why real ISAs are
easier to teach than they look.

\begin{checkpoint}[the one addressing mode]\label{cp:addr05}
Every RV32I memory instruction is \texttt{offset(base)}. Indexed,
auto-increment and PC-relative modes from bigger ISAs simply don't
exist --- simplicity is the point of RISC. Predict how a C
\texttt{p[i]} loop compiles: \texttt{lw} with a computed base, or
\texttt{addi} the base between iterations. Ch03's arrsum did the
second.
\end{checkpoint}

\section{Running it: 13 words, checked state}
\label{sec:run05}

\begin{example}[the first real program]\label{ex:run05}
\texttt{ch05\_prog.hex} is thirteen words produced by the book's own
assembler --- arithmetic, a store, a load back, a taken branch, a
\texttt{lui}. The testbench plays instruction and data memory around
\texttt{rv32i\_sc\_top}, runs to the terminal \texttt{jal self}, then
inspects architectural state (the registers and memory a programmer
can see). Output of \texttt{ch05\_sc\_tb}; the original capture on the
author's Mac (Icarus 13) and the re-run in the Linux x86\_64 container
(Icarus 12) print the same lines:
\begin{lstlisting}
ran 12 cycles, pc parked at 00000030
  ok: a0 = 1
  ok: a1 = 2
  ok: a2 = a0+a1 = 3
  ok: mem[8] = 3 (sw worked)
  ok: a3 = lw back = 3
  ok: a4 = a3+5 = 8 (beq skipped 99)
  ok: a5 = a4-a2 = 5
  ok: a6 = lui 0x12345000
CPI check: 12 instrs retired in 12 cycles (CPI=1 by construction)
ch05 PASS
\end{lstlisting}
Count the instructions: thirteen words, but the taken \texttt{beq}
skips one, so eleven run before the pc reaches the parking
\texttt{jal} at address 48, and that \texttt{jal} runs once more
before the testbench stops: twelve cycles, twelve instructions. The
reference simulator of ch03 independently reports eleven before the
park. One instruction per cycle, as designed.
\end{example}

\begin{principle}[Think like this: watch the machine think]
When you do not trust a design, make it show its work. The testbench
can print, every cycle, the pc, the instruction word, the immediate
the generator produced, the ALU output and the next pc. Reading that
table beside the assembly is the hardware equivalent of printing
variables in a program.
\end{principle}

\begin{example}[decode a word by hand --- naive attempt first]\label{ex:fields05}
Take the word \texttt{0x00c02423}. A tempting first try: ``every
instruction has its constant in the top twelve bits'', so read bits
31:20 and call it the immediate. That gives
$\texttt{0x00c}=12$. Now the correct split. Bits 6:0 are
\texttt{0100011}: the \emph{store} opcode, so the format is S-type, in
which the constant is cut in two to keep \texttt{rs1} and \texttt{rs2}
in fixed places. Bits 31:25 are 0 and bits 11:7 are 01000, so the
immediate is $(0\ll5)\,|\,8=8$. Bits 19:15 give \texttt{rs1}=0, bits
24:20 give \texttt{rs2}=12 (\texttt{a2}). The word is
\texttt{sw a2,8(zero)}. The ``12'' of the naive reading was the
\emph{register number} of \texttt{a2}, not an offset. The script
\texttt{ch05\_fields.py} does this for every word and prints the wrong
(naive) immediate in the last column:
\begin{lstlisting}
addr word     fmt op     rd rs1 rs2  imm(used)    immI(wrong)
0000 00100513  I   addi   10   0   -  1            1
0004 00200593  I   addi   11   0   -  2            2
0008 00b50633  R   add    12  10  11  -            11
000c 00c02423  S   sw      -   0  12  8            12
0010 00802683  I   lw     13   0   -  8            8
0014 00568713  I   addi   14  13   -  5            5
0018 00100293  I   addi    5   0   -  1            1
001c 00550463  B   beq     -  10   5  8            5
0020 06300713  I   addi   14   0   -  99           99
0024 40c707b3  R   sub    15  14  12  -            1036
0028 00078463  B   beq     -  15   0  8            0
002c 12345837  U   lui    16   -   -  0x12345000   291
0030 0000006f  J   jal     0   -   -  0            0
\end{lstlisting}
The test script checks that the immediates in the ``used'' column are
exactly the \texttt{imm} values the Verilog printed in the trace of
the previous example (nine immediates, all equal): two independent
implementations of the scrambler agree.
\end{example}

\begin{principle}[Think like this: two implementations, one answer]
A single implementation can be wrong in a way you cannot see, because
you wrote the test with the same misunderstanding. Writing the same
thing twice in two different styles (here: Python bit arithmetic and
Verilog wiring) and demanding they agree catches the misunderstandings
that do not repeat. Engineers call the trusted second model a
\emph{golden model} or \emph{reference model}.
\end{principle}

\begin{example}[a loop, with the golden model]\label{ex:loop05}
Now a program with a loop: the sum $1+2+\dots+10$ (\texttt{ch05\_sum.S}).
\begin{lstlisting}
        li   t0, 1            # i = 1
        li   t1, 0            # s = 0
        li   t2, 11           # stop when i == 11
loop:   add  t1, t1, t0       # s += i
        addi t0, t0, 1        # i += 1
        bne  t0, t2, loop     # taken 9 times, falls through once
        sw   t1, 0(zero)      # mem[0] = 55
        lw   a0, 0(zero)      # a0 = 55
        addi a1, a0, 1        # load-use: needs a0 right after the lw
        sw   a1, 4(zero)      # mem[1] = 56
halt:   j    halt             # park here
\end{lstlisting}
\emph{What went wrong first.} The shipped version of this core
decided ``take the branch'' from instruction bit 14, which is set for
\texttt{blt}/\texttt{bge} but not for \texttt{bne}. A \texttt{bne}
therefore behaved like \texttt{beq}, the loop exited after one
iteration, and nothing in the 13-word program of the previous example
could notice, because that program has only \texttt{beq}. The cure is to
use bit 12 of the instruction (the low bit of \texttt{funct3}:
0 for \texttt{beq}, 1 for \texttt{bne}). I found this by reading the
decoder while preparing this program; the loop below is now the
regression test for it. Only \texttt{beq} and \texttt{bne} are
implemented; \texttt{blt}/\texttt{bge} are not.

Count by hand first. Three setup instructions, ten trips round a
three-instruction loop, four tail instructions: $3+30+4=37$. The
generic testbench (\texttt{ch05\_run\_tb.v}) runs the core and
prints its final state; the golden model (the ch03 simulator, driven
by \texttt{ch05\_golden.py}) prints its own. Hardware output
(Linux x86\_64 container, Icarus 12):
\begin{lstlisting}
CORE=single-cycle F=37 stalls=0 taken=0 lastret=-1
x5=0000000b
x6=00000037
x7=0000000b
x10=00000037
x11=00000038
m0=00000037
m1=00000038
\end{lstlisting}
\texttt{x6}=\texttt{0x37}=55, \texttt{x10}=55, \texttt{x11}=56, memory
words 0 and 1 hold 55 and 56. The line ``F=37'' says the parking
instruction was first fetched after 37 cycles, and the golden model
says $I=37$ instructions executed. The test script diffs the two
state dumps and checks $F=I$. (The \texttt{taken} counter only
exists in the pipelined cores; ignore it here.)
\end{example}

\begin{example}[proving \texttt{x0} is hardwired --- and breaking it on purpose]\label{ex:x0test05}
How do you test ``nothing happens''? Naively: write to \texttt{x0},
read it back, see 0. That test passes on a broken design too if the
read side is also hard-wired to zero. A better program tries to
\emph{use} the corrupted value (\texttt{ch05\_x0.S}):
\begin{lstlisting}
        addi x0, x0, 7        # must be silently dropped
        lui  x0, 0x12345      # so must this one
        addi a0, x0, 1        # a0 = 0 + 1 = 1   (a0 = 8 if x0 were 7)
        add  a1, x0, a0       # a1 = 0 + 1 = 1
        addi a2, zero, 3      # a real write still lands: a2 = 3
halt:   j    halt
\end{lstlisting}
The correct core ends with \texttt{a0}=1, \texttt{a1}=1, \texttt{a2}=3
(and the golden model agrees). Then the test script builds a
\emph{mutant}: a copy of the register file with both protections
removed (writes to \texttt{x0} allowed, reads of \texttt{x0} not forced
to zero) and demands that the test \emph{fail}. It does:
\begin{lstlisting}
CORE=single-cycle F=5 stalls=0 taken=0 lastret=-1
x10=12345001
x11=2468a001
x12=12345003
\end{lstlisting}
Check it by hand: after the \texttt{lui}, the mutant's \texttt{x0} is
\texttt{0x12345000}; so \texttt{a0}=\texttt{0x12345000}+1,
\texttt{a1}=\texttt{0x12345000}+\texttt{0x12345001}=\texttt{0x2468a001},
\texttt{a2}=\texttt{0x12345000}+3. A test that cannot fail on a broken
design proves nothing; checking that the test \emph{does} fail on a
deliberately broken design is called \emph{mutation testing}.
\end{example}

\begin{example}[sim speed as a measurement]\label{ex:simspeed05}
\texttt{ch05\_spin\_tb} runs a seven-instruction arithmetic loop for a
fixed 2000 cycles (the loop count is not a round number: after
$4+7\times285=1999$ instructions \texttt{a0} holds 285, \texttt{0x11d};
the testbench simply stops at 2000 cycles). The author's Mac
(Apple silicon, Icarus 13) reported \textbf{9\,ms} wall-clock with
\texttt{time vvp}, i.e.\ about 220\,k retired instructions per second.
\emph{Re-measured on the Linux x86\_64 container} (Xeon 2.8\,GHz,
4 cores, Icarus 12): five runs of the same 2000-cycle testbench took
21--24\,ms, but that is mostly process start-up, so it cannot give a
rate. The honest rate comes from a long run of the generic testbench:
200\,000 cycles took 5.9, 6.1 and 6.5\,s, i.e.\ roughly 33\,k retired
instructions per second. The two numbers are far apart partly because
the machines differ and partly because the Mac figure came from a
run so short that it was dominated by start-up; treat the Mac
\emph{rate} with suspicion and the Linux figure as the one that was
measured with a long enough run. Either way, the lesson stands:
simulation is thousands of times slower than silicon, which is why
real CPU verification uses FPGA prototypes, and why our testbenches
stay small and self-checking.
\end{example}

\begin{example}[the combinational loop that hung the simulator]\label{ex:loop-bypass05}
Our register file has an optional \emph{write bypass}: if the same
cycle both writes register $k$ and reads register $k$, the read
returns the value being written (pipelines need this; ch06 explains
why). The first attempt used one register file for both the pipelines
and this single-cycle core. Then the spin program, whose loop contains
\texttt{addi a0,a0,1}, never finished: with the bypass on, the read of
\texttt{a0} equals the write data, the write data is the ALU output,
and the ALU output depends on the read of \texttt{a0}. That is a
circular chain of gates with no register in it, a \emph{combinational
loop}, and the simulator re-evaluates it forever at time zero.
Measured: \texttt{vvp} was still running after 100\,s (killed by
\texttt{timeout}). The fix is a Verilog parameter \texttt{BYPASS}
(default 1 for the pipelines, 0 for this core). Afterwards the same
2000-cycle run finishes in about 22\,ms. The general lesson: a wire
may not depend on itself without a clock edge in between.
\end{example}

\section{Why single-cycle wastes time}
\label{sec:critpath05}
\index{critical path}\index{CPI}

\begin{example}[the \texttt{lw} tax]\label{ex:crit05}
\texttt{lw} travels fetch $\to$ decode+regfile $\to$ ALU $\to$ data
memory $\to$ writeback --- every hardware stop in one period. If each
stage costs about the same delay, the clock period must be $5\tau$.
\texttt{add} finishes in $3\tau$ and idles $2\tau$; \texttt{sw}
idles one. The critical-path figure shows the idle tail: single-cycle
CPI=1 is honest, but the \emph{clock} is five times slower than any
stage needs. Pipelining's promise is exactly that reclaimed tail.
\end{example}

\begin{checkpoint}[predict CPI=1's cost]\label{cp:cpi05}
If the five stages each cost $\tau$ and the register file adds
$\delta$, what's the best achievable clock for the single-cycle core
vs a 5-stage pipeline on the same blocks? $(5\tau+\delta)$ vs
$(\tau+\delta)$: the pipeline's ceiling is the stage time plus
register overhead --- the theme of ch06.
\end{checkpoint}

\section{Common mistakes}
\label{sec:mistakes05}
\begin{itemize}
\item \textbf{Writing \texttt{x0}.} Forgetting \texttt{wa!=0} makes
      \texttt{li x0,5} stick --- every ``hardwired'' invariant breaks.
\item \textbf{Branch on the wrong field.} \texttt{immB} needs the
      shifted splice, not \texttt{immI}: a \texttt{beq} that reads
      \texttt{immI} lands two bytes off silently.
\item \textbf{Muxing before reading.} Using \texttt{rd2} for the
      ALU-B input unconditionally breaks \texttt{lw}/\texttt{sw} ---
      the register file reads the address \emph{register}, the
      immediate is the offset.
\item \textbf{Testing only R-types.} A decode bug in \texttt{sw}
      shows nothing until memory is checked --- the testbench inspects
      \texttt{dmem}, not just registers.
\item \textbf{Believing CPI=1 is fast.} It is honest and it is slow:
      latency hidden by a slow clock is still latency.
\end{itemize}

\begin{itemize}
\item Datapath/control/imm-gen design follows COD ch4 and DDCA ch7;
      adapted to our rv32i\_* module split.
\item The original captures are from Icarus Verilog 13.0 on the
      dev box (arm64 macOS). Every output re-run for this edition is
      labelled ``Linux x86\_64 container'' (Icarus 12.0) and comes from
      \texttt{code/test\_ch05.sh}; program bytes are assembled by
      \texttt{ch03\_rv32asm.py}.
\item Two defects found while re-running: the single-cycle core
      treated \texttt{bne} as \texttt{beq} (decoded from the wrong
      bit), and the shared register file's write bypass made a
      combinational loop in this core. Both are fixed in the code
      shipped with this edition. The testbench line ``12 instrs retired''
      used to be a hard-coded constant; it now prints the measured
      cycle count.
\item \texttt{blt}/\texttt{bge} are not decoded (only \texttt{beq} and
      \texttt{bne}); the ch03 programs that use them run on the ch03
      simulator, not on this core.
\end{itemize}

\section{Exercises}
\label{sec:exercises05}

\begin{exercise}[easy]\label{ex:e05a}
Which control wires does \texttt{jal} assert, and why is
\texttt{wbsel=pc+4}?
\end{exercise}
\begin{solution}[hint]
regwrite + jump; the destination register must capture the return
address.
\end{solution}

\begin{exercise}[easy]\label{ex:e05b}
Why is \texttt{x0}'s write-enable explicitly masked in the regfile
rather than trusted to software?
\end{exercise}
\begin{solution}[hint]
Hardware invariant: a stray \texttt{sw}-style bug or bad codegen
must not corrupt the constant zero.
\end{solution}

\begin{exercise}[medium]\label{ex:m05a}
Trace \texttt{lw a3,8(zero)} through every block of the datapath:
what does each output wire carry?
\end{exercise}
\begin{solution}[hint]
PC=0x10; decode: alusrc=1, memread=1, wbsel=mem; rd1=0;
ALU=8; dmem[2]=3; wb=3 $\to$ a3.
\end{solution}

\begin{exercise}[medium]\label{ex:m05b}
The imm generator scrambles five shapes in parallel with the regfile
read. Why is the parallelism safe even when an instruction doesn't
need an immediate?
\end{exercise}
\begin{solution}[hint]
The mux only selects when alusrc=1; wasted scrambling costs power,
not correctness.
\end{solution}

\begin{exercise}[medium]\label{ex:m05c}
\texttt{sub} and \texttt{beq} share \texttt{aluop=sub}. What differs
in their control words and why can the ALU be shared?
\end{exercise}
\begin{solution}[hint]
beq sets branch, no regwrite; the subtract output is used only as
the zero flag --- ALU is a function of inputs, free to share.
\end{solution}

\begin{exercise}[medium]\label{ex:m05d}
Our core ran 12 instructions in 12 cycles but the program was 13
words. Reconcile.
\end{exercise}
\begin{solution}[hint]
Words 0--7 and 9--11 execute (eleven instructions); word 8
(\texttt{addi a4,zero,99}) is skipped because the taken \texttt{beq}
sets the next pc to $\texttt{0x1c}+8=\texttt{0x24}$. Eleven plus
one execution of the parking \texttt{jal} at \texttt{0x30} is twelve.
In a single-cycle core the skipped word is never even fetched.
\end{solution}

\begin{exercise}[medium]\label{ex:m05e}
Estimate the same-loop sim speed if the tb also dumped a VCD ---
does the core get slower, or only the log?
\end{exercise}
\begin{solution}[hint]
Both: event-driven sim slows with more dumped signals; the RTL is
unchanged. Measurement vs mechanism.
\end{solution}

\begin{exercise}[hard]\label{ex:h05a}
The decoder already handles \texttt{slt} and \texttt{slti}
(find them). The ALU also has an unsigned compare (\texttt{op}=8) that
no instruction reaches. Which decoder rows must change to add
\texttt{sltu} and \texttt{sltiu}, and which two register values
distinguish a signed from an unsigned compare?
\end{exercise}
\begin{solution}[hint]
In the R-type case add the arm \texttt{\{f7[5],f3\}=0\_011} $\to$
\texttt{aluop=8}; in the I-type case add \texttt{f3=011} $\to$
\texttt{aluop=8}. Nothing else changes. Test values: $a=-1$
(\texttt{0xffffffff}) and $b=1$: signed says $-1<1$ (result 1),
unsigned says $4294967295<1$ is false (result 0). (Not run here: the
ch03 assembler has no \texttt{sltu}.)
\end{solution}

\begin{exercise}[hard]\label{ex:h05b}
The critical-path argument assumed equal stage delays. If decode is
actually 2$\tau$, which instruction is now critical and does the
single-cycle case get better or worse relative to pipelining?
\end{exercise}
\begin{solution}[hint]
Still \texttt{lw} (it's the superset path); single-cycle gets
\emph{worse} --- its period grows while the pipeline's is set by the
slowest stage.
\end{solution}

\begin{exercise}[hard]\label{ex:h05c}
Design a self-checking test that proves \texttt{x0} is hardwired:
write to it via \texttt{addi x0,x0,7} then read it. What else must
the tb check to catch a lazy \texttt{we}?
\end{exercise}
\begin{solution}[hint]
x0 must still read 0 after the write; also check a real write to a
nonzero reg landed (proving we wasn't masked globally).
\end{solution}


\begin{exercise}[easy]\label{ex:e05c}
In the trace of the chapter, which line shows the pc \emph{not} moving
by 4, and what was the instruction there?
\end{exercise}
\begin{solution}[hint]
Line T7: \texttt{pc=0x1c} and next is \texttt{0x24}, the taken
\texttt{beq a0,t0,+8}.
\end{solution}

\begin{exercise}[easy]\label{ex:e05d}
Decode \texttt{0x00c02423} again, this time naming only the opcode
and which two fields hold the split immediate.
\end{exercise}
\begin{solution}[hint]
Opcode \texttt{0100011} (S-type, store). The immediate is
\texttt{insn[31:25]} (high 7 bits, here 0) joined with
\texttt{insn[11:7]} (low 5 bits, here 8): offset 8.
\end{solution}

\begin{exercise}[medium]\label{ex:m05f}
The loop program has a \texttt{bne} at address 20 (\texttt{0x14}) whose
target \texttt{loop} is at address 12. Compute the branch offset and
write its 13-bit \texttt{immB} pattern. The assembled word is
\texttt{0xfe729ce3}: confirm that its bits agree.
\end{exercise}
\begin{solution}[hint]
Offset $=12-20=-8$. In 13 bits (bit 0 is always 0) that is
\texttt{1\_1111\_1111\_1000}. The word splits as: bit 31 $=1$ (imm[12]),
bits 30:25 $=111111$ (imm[10:5]), bits 11:8 $=1100$ (imm[4:1]),
bit 7 $=1$ (imm[11]); reassembled it is \texttt{1 1 111111 1100 0}
$=-8$. The \texttt{ch05\_fields.py} output shows \texttt{-8} for this word.
\end{solution}

\begin{exercise}[medium]\label{ex:m05g}
Without running anything, predict the number of instructions executed
by \texttt{ch05\_sum.S} if the loop bound were 6 instead of 11
(\texttt{li t2, 6}, so the loop runs for $i=1\dots5$).
\end{exercise}
\begin{solution}[hint]
Setup 3, five trips of 3 instructions $=15$, tail 4: $3+15+4=22$.
\end{solution}

\begin{exercise}[medium]\label{ex:m05h}
Hypothetical stage delays (not measured): fetch 250\,ps, register read
150\,ps, ALU 300\,ps, data memory 400\,ps, register write 100\,ps.
Find the delay of \texttt{add}, \texttt{sw}, \texttt{lw}, \texttt{beq}
and the clock period of a single-cycle core. What is the ideal
throughput ratio against a five-stage pipeline whose period is its
slowest stage plus 50\,ps of register overhead?
\end{exercise}
\begin{solution}[hint]
\texttt{add}: $250+150+300+100=800$\,ps. \texttt{sw}: $250+150+300+400=1100$.
\texttt{lw}: $250+150+300+400+100=1200$. \texttt{beq}: $250+150+300=700$.
Period $=1200$\,ps (the \texttt{lw}). Pipeline period $=400+50=450$\,ps.
Ratio $1200/450\approx2.67$, well below the ideal 5 because the stages
are unequal.
\end{solution}

\begin{exercise}[medium]\label{ex:m05i}
Starting from the mutant output of the chapter
(\texttt{x10=12345001}, \texttt{x11=2468a001}, \texttt{x12=12345003})
write one sentence explaining what the mutant's \texttt{x0} must have
held, and verify the middle value by adding in hexadecimal.
\end{exercise}
\begin{solution}[hint]
\texttt{x0}$=$\texttt{0x12345000} (the last write, the \texttt{lui}).
\texttt{0x12345000}+\texttt{0x12345001}: low parts
\texttt{0x000}+\texttt{0x001}$=$\texttt{0x001}, high parts
\texttt{0x12345}+\texttt{0x12345}$=$\texttt{0x2468a}, giving
\texttt{0x2468a001}.
\end{solution}

\begin{exercise}[hard]\label{ex:h05d}
Explain exactly why a write bypass in the register file makes the
single-cycle core hang on \texttt{addi a0,a0,1}, naming the wires in
the loop. Why does the same bypass cause no loop in a pipelined core?
\end{exercise}
\begin{solution}[hint]
With bypass, \texttt{rd1}$=$\texttt{wd} whenever \texttt{wa==ra1};
\texttt{wd} is the writeback mux output, which for \texttt{addi} is
\texttt{alu\_y}$=$\texttt{rd1}$+1$. So \texttt{rd1} $=$
\texttt{rd1}$+1$, a cycle with no register in it. In the pipeline the
write data comes from the MEM/WB register (the \emph{previous}
instruction), so the chain passes through a flip-flop and is not a loop.
\end{solution}

\begin{exercise}[hard]\label{ex:h05e}
A mutant register file lets \texttt{x0} be written but still forces
reads of \texttt{x0} to 0. Does \texttt{ch05\_x0.S} catch it? Argue
from the program, then say what kind of test would be needed if not.
\end{exercise}
\begin{solution}[hint]
No: every read of \texttt{x0} still returns 0, so \texttt{a0}, \texttt{a1}
come out right and the final dump of \texttt{x1}--\texttt{x31} is the
same (\texttt{x0} itself is not in the dump). This mutant cannot be
seen through the architectural state, so it is harmless by definition;
a test would have to peek at the internal array (\texttt{dut.rf.x[0]}).
Mutation testing calls such cases ``equivalent mutants''.
\end{solution}
